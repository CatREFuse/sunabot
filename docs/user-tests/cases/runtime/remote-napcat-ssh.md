# 本地 Core 连接远端 NapCat

## 用户目标

管理员将两个 QQ 的 NapCat 迁移到 ECS，本地继续运行 Sunabot Core。现有账号、登录目录、记忆和配置保留，管理台继续显示实际连接状态并支持刷新登录二维码。

## 角色与环境

- 角色：部署管理员；无主对话、外部 Provider 或 QQ 主动发送。
- 本地 Linux/WSL Native Core，远端 Linux amd64/arm64 Docker，每个 QQ 一个 NapCat。
- 专用 SSH 密钥、固定 known_hosts，远端仅向私有 Docker 网桥转发 OneBot，WebUI 通过回环转发访问。
- 单元夹具使用合成账号与隔离目录；实机切换需要用户确认。

## 输入与预期结果

1. 未配置远端时，本地运行行为保持不变。
2. 配置远端后，Docker 探测、账号启动、停止、重启和日志均指向同一远端；远端不可达时报告错误，不启动本机 QQ。
3. 配置同步仅传输 NapCat 配置与入口文件，不传输 Core runtime.env、Provider 密钥、业务 SQLite 或人格。
4. 远端二维码使用原始修改时间，刷新必须等待内容变化，过期图不展示。手动登录标记、快速登录账号和二维码删除发生在对应远端账号目录。
5. `restart-core` 保留远端容器及登录目录。仅隧道断开和重连不重启 QQ。
6. 管理台和 OneBot 不公开监听公网；SSH 主机密钥不匹配、鉴权失败及文件操作失败均明确报错。
7. 切换前停止本机对应 QQ 并保存恢复点，完成最终登录目录同步后启动远端，不能同时登录同一 QQ。

## 验证与质量标准

- 合成夹具核对 SSH 参数、命令引用、配置白名单、路径映射、失败传播和二维码时效。
- 独立夹具评审检查机械断言与质量，模拟结果不计为真实 QQ 验收。
- 运行相关单元测试、harness 自检、runtime contract、类型检查、构建和既有 Core 重启回归。
- 实机记录容器 ID、登录状态、OneBot 心跳、自然入站、端口监听、Swap、OOM 和磁盘余量。
- 未切换、未扫码、未观察到真实消息或未进行 arm64 实机运行时，分别记录未验证。

## 每账号缓存上限

部署管理员要求每个 QQ 的缓存超过 1 GiB 时自动清理。隔离夹具在两个账号目录分别创建稀疏媒体、QQ 日志、登录文件与消息库，不连接 Provider 或发送 QQ 消息。

- 每分钟检查一次，每账号独立累计已知媒体、临时文件及日志目录的普通文件大小；恰好 1 GiB 不清理，超过后按修改时间从旧到新清理至不超过 1 GiB。
- dry-run 不改文件；`--apply` 才执行，`--purge-cache` 配合 apply 用于管理员要求的一次性缓存清空。
- 登录目录、配置、消息数据库和 Sunabot 业务数据保留；自动任务不清空消息库。
- 不跟随符号链接，不删除扫描后被替换或修改的文件；清理后仍超限或发生权限错误必须明确失败。
- 夹具验证账号隔离、阈值边界、旧文件优先、登录/数据库保留、链接边界及实际释放量，独立评审不修改产品代码。
